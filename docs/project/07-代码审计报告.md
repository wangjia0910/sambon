### 0.2 关键结论

1. **C-01（Critical，后端，未修复）**：验收/裁定/自动验收的结算路径在**无显式 event_id 或并发**时可重复结算，已用运行时并发实测确认双花（单次 100 SBC 赏金被结算成 200）。**正式运营前必须修复**。
2. **前端 C-A/C-B（Critical，已修复）**：DOM 挂载点 ID 错配（`wow-*` vs HTML 的 `m-*`）导致 demo 首页白屏、人工闸门失效；`silent401` 未处理导致匿名访客被强制跳登录页、SEO 口号区不可达。两者均由运行时 DOM shim 实测复现并已修复（详见 §3.1、§5）。
3. **PII 脱敏缺陷（已修复）**：`sanitizeSubmissionText` 对 ≥6 位超长连续数字串无兜底，已补 `\d{6,}` 规则并运行时验证（详见 §4.1）。
4. 其余 High/Medium 项多为**幂等/CAS 一致性**与**运维令牌强度**问题，在演示环境不构成实际风险，但应在开放运营前逐项处置。

## 2. 发现清单（按严重级别）

### 2.1 Critical

#### C-01 结算路径缺少幂等/CAS，并发验收可导致重复结算（双花）

- **位置**：`prod/lib/api.js` `hVerify:953-997` → `settleTask:350-...`；`hDispute(resolve):1030+`；`hAdminCron:1577+` 的超时自动验收分支。
- **证据（静态）**：`settleTask` 中状态更新为
  `UPDATE tasks SET state='SETTLED', ... WHERE task_id=?`（`api.js:389` 附近），**无 `AND state='SUBMITTED'` 或 `AND version=?` 条件**；`postLegs` 每次调用都新写一批账本腿（`eventId || uuid('EVT')`）。
- **证据（运行时实测）**：在内存 D1 mock 上构造"发布→审核→推送→接单→提交"链路后，对同一任务并发发起两次 `POST /api/tasks/:id/verify`（`decision=approve`，不同 event_id）：
  - 两次均返回 `200`；
  - `subject:escrow` 账本腿 **3 条**（正常应 1 条），总 delta `-105`；
  - 接单人入账腿 **2 条**（正常应 1 条），总额 **200**（正常应 100）；
  - 任务状态 `SETTLED`，version 从 6 跳到 8（两次写）。
- **影响**：赏金被重复转付，账本虽仍"守恒"（ legs 成对），但**经济含义错误**——平台资金被超额支付。带显式不同 event_id 时幂等层无法拦截；不带 event_id 时 `withIdempotency` 直接 `return fn()`，完全没有保护。
- **触发条件**：同一任务被并发验收（两个请求几乎同时到达，均在对方写入前通过 `row.state==='SUBMITTED'` 检查）。单用户顺序操作不触发。
- **修复建议（正式运营前必做）**：
  1. **数据库级互斥（推荐）**：新增 `settlement_guards(task_id TEXT PRIMARY KEY, created_at)` 表。结算前先 `INSERT OR IGNORE INTO settlement_guards(task_id, ...) VALUES(?,...)`，`changes===0` 则拒绝（409 `SETTLEMENT_IN_PROGRESS`）；插入成功者才执行 `settleTask` 的 batch。利用唯一主键的原子性彻底消除 TOCTOU。
  2. **状态 CAS（补充）**：`settleTask` 的状态更新改为 `UPDATE tasks SET state='SETTLED', ... WHERE task_id=? AND state='SUBMITTED'`，并在 batch 后校验 changes；为 0 则整批回滚（需在事务内先做守卫写）。
  3. **服务端确定性幂等键（补充）**：对 approve/auto_accept/dispute-resolve 分支，当调用方未传 event_id 时，服务端注入 `settle:<task_id>:<target_state>` 作为幂等键，使重复请求在 `withIdempotency` 层被拦截。
  4. 三项同时实施并补充并发回归用例（断言"并发 N 次仅 1 次结算、入账腿数=1"）。
- **风险接受说明**：当前为演示/评审环境，不开放真实资金与多用户并发，**本轮不改核心资金逻辑**（避免仓促引入新缺陷）；已作为正式运营的一号上线阻塞项登记。

### 2.2 High

#### H-01 管理员审核（review）无幂等保护
- **位置**：`hReview:743+`。`withIdempotency(c.db, c.body, ...)` 依赖调用方 event_id；前端操作台 `app.js` 传了 event_id，但**直接 API 调用可不带**。
- **影响**：并发/重试审核可重复冻结（`CreditFrozen`）与改状态。审核是 admin 人工动作，重复冻结会锁定超额 SBC。
- **建议**：同 C-01，对状态变更型人工动作加服务端确定性幂等键 + CAS。

#### H-02 争议裁定（dispute resolve）pay_solver 分支共用 C-01 缺陷
- **位置**：`hDispute:1030+` resolve 分支调用 `settleTask`。
- **影响**：与 C-01 同源，争议裁定为 pay_solver 时可重复结算。
- **建议**：随 C-01 一并修复（settlement_guards 守卫）。

#### H-03 超时自动验收（cron auto_accept）无幂等/CAS
- **位置**：`hAdminCron:1577+` 及 `jobs.js` 超时工单触发的自动验收。
- **影响**：超时任务若被并发触发自动验收，同样重复结算。cron 由外部调度器调用，重试机制可能导致重复投递。
- **建议**：cron 处理的目标 task 列表需带"已处理"标记（写入 settlement_guards 或独立 processed 表），确保 at-most-once。

#### H-04 CSRF 豁免的公开写端点可被重放
- **位置**：`POST /api/consents`、`/api/auth/verify-email`、`/api/admin/bootstrap`、`/api/admin/cron` 无 CSRF（设计如此）。
- **影响**：`consents` 与 `verify-email` 是幂等可接受的；但 `admin/bootstrap` 与 `cron` 依赖独立令牌（bootstrap_token / CRON_SECRET）。风险在于令牌通过**请求体**传递时可能被日志/代理记录。
- **建议**：`X-Cron-Secret` header 方式已支持（优先使用），文档明确禁止在 body 传令牌；bootstrap 完成后应移除 `ADMIN_BOOTSTRAP_TOKEN` 环境变量（wrangler.toml 注释已提示，需运营落地）。

### 2.3 Medium

#### M-01 登录失败计数与账号锁定存在竞态窗口
- **位置**：`prod/lib/risk.js` + `hLogin`。失败计数自增与锁定判断非原子，并发爆破可绕过锁定阈值。
- **建议**：用单条 `UPDATE ... WHERE` 原子递增并返回计数，或 D1 batch 内完成。

#### M-02 全局限流按 IP+UA 哈希，代理后 IP 可能失真
- **位置**：`api.js:1714` `rateLimit(global, 180)`。Cloudflare 场景应使用 `CF-Connecting-IP`。
- **建议**：优先读取 `CF-Connecting-IP` 头（经 Cloudflare 可信注入），回退到现有逻辑。

#### M-03 `withIdempotency` 的 pending 状态在进程崩溃后残留
- **位置**：`api.js:251-278`。若进程在 `pending` 写入后、`done` 更新前崩溃，该 event_id 永久 409。
- **建议**：给 pending 加 TTL（如 5 分钟），查询时对过期 pending 自动清理/重试。

#### M-04 法务页 `noindex` 与主站 SEO 定位的合规张力
- **位置**：`prod/site/legal.html:6` 保留 `noindex, nofollow`，而主入口 `member.html` 已改 `index, follow`。
- **影响**：SEO 收录主站但法务页不收录，可能出现"收录了产品页但合规声明不可见"的呈现缺口。Google 通常需要能抓到隐私/条款页以理解站点性质。
- **建议**：将 legal.html 也改为 `index, follow`（其内容为公开合规声明，不含敏感信息），或至少有 `X-Robots-Tag` 一致性策略。**已在本轮处置（见 §4.2）**。

#### M-05 sitemap 未覆盖 hash 路由的具体任务/榜单页
- **位置**：`prod/site/sitemap.xml` 仅列 `/` 与 `/legal.html`。
- **影响**：SPA 的 `#/hall`、`#/rank` 等 hash 路由不被搜索引擎作为独立 URL 收录（hash 不发送到服务端，这是 SPA 通用限制）。
- **建议**：当前可接受（核心内容已在首页静态区块 + 结构化数据中呈现）；若需深度收录，改用 History API + 服务端渲染或预渲染。作为长期改进登记。

### 2.4 Low

#### L-01 错误信息中 `X-Idempotent: replayed` 可能暴露内部机制
- 影响极低，属正常幂等语义。无需处理。

#### L-02 `dev_token` 回显仅在 `EMAIL_VERIFICATION_DEV_ECHO=true` 时发生
- 生产该变量留空即不回显（wrangler.toml 已注明"生产严禁设置"）。属配置纪律项。

#### L-03 前端 toast 直接显示 `error.message`
- **位置**：`member.js` / `app.js` 的 `showError`。后端错误消息为中文提示（不含堆栈/SQL），可控。无敏感泄露。

#### L-04 审计脚本自身的字符串匹配可能被未来重构误伤
- 属测试维护成本，非代码缺陷。

## 3. 前端 / 构建 / 测试 / SEO 审计

> 本节为前端专项审计结论。方法：静态精读 + **运行时 DOM shim 执行真实 `member.js`**（`tests/verify-member-runtime.mjs`）。
> 说明：两名审计代理独立给出结论，存在分歧处已由主代理逐条复核源码后裁决（见 §3.4）。

### 3.1 Critical（已修复）

#### C-A DOM 挂载点 ID 错配 → demo 首页白屏 / 人工闸门失效
- **位置**：`prod/site/member.js`：`toast()`、`humanConfirm()`/`closeModal()`、`bootstrap()` 三处。
- **证据**：JS 引用 `getElementById('wow-toast')`/`('wow-modal')`/`('wow-banner-demo')`，而 `member.html` 实际 id 为 `m-toast`/`m-modal`/`m-demo-banner`（其余全部元素均用 `m-*` 前缀，仅这三处写错）。
- **影响**：
  - demo 模式（`state.mode !== 'production'`）下 `bootstrap()` 执行 `getElementById('wow-banner-demo').hidden = false` 抛 `TypeError: Cannot set properties of null`，`render()` 永不执行 → **首页白屏**；
  - 人工闸门 `humanConfirm()` 取不到 `wow-modal` → 验收/争议/取消的二次确认弹窗失效（合规人工闸门在 UI 层断链）；
  - 任何 `toast()`（含错误提示）取不到 `wow-toast` → 二次异常。
- **运行时复现**：DOM shim 加载真实源码，注入 `wow-banner-demo` 后 `bootstrap` 抛出与线上完全一致的 `Cannot set properties of null (setting 'hidden')`（负向自检已验证）。
- **修复**：三处 JS 引用统一改为 HTML 的 `m-*` id。已加 `VM-28/VM-29` 静态契约断言 + `RT-02/RT-05` 运行时断言锁定。

#### C-B 匿名访客 silent401 未处理 → 强制跳登录页 / SEO 口号区不可达
- **位置**：`prod/site/member.js` `api()` 的 401 分支（原 `:319-324`）与 `bootstrap()`（`:899`）。
- **证据**：`bootstrap()` 以 `api('/api/auth/me', { silent401: true })` 做匿名探测，但 401 分支只判断 `opts.authAttempt`，未识别 `silent401`，执行 `clearSession(); go('#/auth')`；而 `GET /api/auth/me` 不在后端 `PUBLIC_ROUTES`。对照组 `app.js:1086` 正确实现 `if (opts.silent401) return null;`。
- **影响**：未登录访客访问站点根路径（重写到 member）时被强制跳到 `#/auth`，且 `member.js` 在 auth 路由隐藏 SEO 引导区 → 含核心口号「无事不登三宝殿」的 `<h1>` 对真实访客与执行 JS 的爬虫均不可达，SEO/AEO 落空。
- **运行时复现**：DOM shim 模拟匿名 401，修复前 `location.hash` 变为 `#/auth`；负向自检（注入移除守卫）确认 `RT-03` FAIL。
- **修复**：401 分支在 `clearSession()` 后加 `if (opts.silent401) return null;`（置于 `go('#/auth')` 之前）。已加 `VM-30` + `RT-03/RT-04` 断言。

### 3.4 代理结论分歧裁决

- 一名代理将 `cloudflare/_headers` 末尾的 `/*` 报为"误用 `/* */` 注释导致 Referrer-Policy 不生效"（L-06）。**经查 Cloudflare 官方文档证伪**：`/*` 是 Pages `_headers` 的合法 match-all 路径模式，命中多规则时头部合并、`#` 才是注释语法。该头实际会下发。**裁决：误报，不改代码**，仅补充 `#` 说明注释。
- 两名代理对 `silent401` 严重级别判断不同（H vs Critical）。**裁决：Critical**——因它与 DOM 错配叠加直接导致站点主入口对匿名访客不可用，且使核心 SEO 口号不可达，影响面为全部访客。

### 3.5 正面结论（经证据确认）

- 无任何硬编码令牌/密钥/真实 PII（`privacy@sambon.net` 为明确标注的占位地址）；无 `eval`/`new Function`/`document.write`/动态脚本加载/CDN/外链资源（CSS 亦无 `@import`/`url(http)`）。

## 4. 审计中发现并已处置的问题

### 4.1 PII 脱敏长数字串残留（已修复）

- **发现**：`sanitizeSubmissionText`（`src/domain.mjs:621`，真源）原实现仅精确匹配 18 位证件号与 11 位手机号，且均带数字边界 `(?<!\d)...(?!\d)`。构造 30 位连续数字串时，两条规则都因边界不满足而不匹配，**整串 30 位数字原样落库**。
- **影响**：拼接号码 / 超长订单号 / 异常输入可绕过脱敏，与"验收须无 ≥6 位连续数字"口径冲突。
- **修复**：在两条精确规则后追加兜底 `.replace(/(?<!\d)\d{6,}(?!\d)/g, ...)`，与事件脱敏 `redactDigits` 口径一致；保持"证件号优先"顺序（精确规则已替换为非数字，兜底不会二次匹配）。
- **验证**：运行时 5 组用例（18 位证件号 / 手机号 / 30 位长串 / 混合 / 5 位短号保留）全部通过；全套 266 项回归全绿。
- **同步**：真源 `src/domain.mjs` 修改后重建，生成副本 `prod/lib/domain.js` 与 `cloudflare/src/domain.mjs` 逐字节一致（P-64/P-65 断言通过）。

### 4.2 法务页 SEO 一致性（已处置）

- 原问题：`legal.html` 保留 `noindex, nofollow`，而主入口已 `index, follow`，出现"收录产品页但合规声明不可见"的呈现缺口。
- 修复：`legal.html:7` 改为 `index, follow, max-snippet:-1`；补 `canonical` 自指、hreflang `zh-CN`/`en`/`x-default`（后两者见 M-F2 的 `?lang=` 落地修复）。
- 连带修复 M-F2：新增 `legal-lang.js` 使 `?lang=` 真正驱动纯 CSS radio 切换，消除"英文 URL 显示中文"的 hreflang 语义错误。
- 断言：`VSX-18c/18d` 全绿。
