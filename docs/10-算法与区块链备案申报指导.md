## 1. 适用性判定（为什么这两项要办）

### 1.1 算法推荐服务备案：明确触发

依据《互联网信息服务算法推荐管理规定》（四部门令第 9 号，2021-12-31 公布，2022-03-01 施行）：

- **第 2 条**：应用算法推荐技术是指利用**生成合成类、个性化推送类、排序精选类、检索过滤类、调度决策类**算法向用户提供信息。
- **第 24 条**：**具有舆论属性或者社会动员能力**的算法推荐服务提供者，应履行备案手续。
- 《具有舆论属性或社会动员能力的互联网信息服务安全评估规定》**第 2 条第（二）项**：「开办提供公众舆论表达渠道或者**具有发动社会公众从事特定活动能力**的其他互联网信息服务」。悬赏互助平台向不特定接单人派发任务、组织线下履约，属于该情形；Web 站若附设信息分享 / 通讯群组等功能，还命中第（一）项列举。

**项目算法 → 法定类型映射**：

| 项目模块（方案 §3 / §4） | 法定算法类型 | 是否需备案 |
|---|---|---|
| 核心推送算法：硬过滤 → 召回 → 粗排 → 精排 → 重排 → 触达编排 | **调度决策类**（主）+ 个性化推送类 | 是 |
| 任务排行榜六维评分与动态更新 | **排序精选类** | 是（同一算法可关联，不必重复立案） |
| 用户积分排行榜 RankScore | **排序精选类** | 是 |
| LLM 适配层：描述抽取、语义匹配附加分、争议材料摘要 | 生成合成类 / 检索过滤类 | 若上线真实模型需另行评估（§1.3） |

> 按 2026-11-09《互联网信息服务算法备案常见问题答疑汇总》：**备案以「算法」为基础单元**；多个产品使用同一算法的无需重复备案，只需把算法关联多个产品；使用多个算法的分别备案。因此应把上述能力**收敛为最小算法单元**申报，避免按页面重复立案；`weight_version` 版本化记录（方案 §4.2）作为变更留痕依据。

### 1.2 区块链信息服务备案：按保守口径准备，最终取决于链选型

依据《区块链信息服务管理规定》（网信办令第 3 号，2019-01-10 公布，2019-02-15 施行）：

- **第 2 条**：区块链信息服务指「基于区块链技术或者系统，通过互联网站、应用程序等形式，**向社会公众提供信息服务**」；提供者包括「向社会公众提供区块链信息服务的**主体或者节点**，以及为区块链信息服务的主体**提供技术支持的机构或者组织**」。
- 2026-11-09《区块链信息服务备案常见问题答疑汇总》明确：**面向外部主体提供区块链底层、节点、存证等 BaaS 相关服务的运营主体，应当履行备案程序**。

项目现状是「许可链 + 链下权威账本 + 链上 Merkle 锚定、零 PII / 零任务正文上链」（方案 §4.1、契约 §5），是否触发需按 **D1 链选型**分三种情形裁定：

| 分支 | 情形 | 备案结论 | 需要的证据 |
|---|---|---|---|
| **① 自建许可链，对外提供存证 / 查询** | 平台自跑节点、向发布方与接单人开放存证凭证查验 | **应备案**，按「应备尽备」办理 | 节点清单、部署位置（境内）、服务说明、安全评估报告 |
| **② 仅调用已备案第三方合规 BaaS** | 平台不自跑节点，仅把 Merkle 根交给供应商锚定 | 平台侧**可能无需单独备案**，但不得自行认定豁免 | 供应商备案编号可核、服务协议、**法务书面意见** |
| **③ 取消链上锚定，仅保留链下权威账本 + 哈希摘要** | 完全不基于区块链技术或系统对外提供信息服务 | 需**书面论证「不属于备案范畴」**，并经法务签字 | 架构说明、法务意见、白皮书相应条款 |

> **主代理口径**：在 D1 未拍板前，一律按 **① 准备材料**，避免临上线才发现缺件；若最终选 ② 或 ③，须由法务出具书面意见并把结论写入白皮书要点 10 与 `docs/07` §2，不得口头豁免。
>
> **服务名称规范**（新答疑）：应清晰体现实际用途、简洁具体、不得夸大或虚构，**不得包含「虚拟货币」「交易所」「ICO」等词汇**。项目 SBC 已定性为平台内贡献积分、非加密资产、不可兑付转让（`COMPLIANCE.md`），与该要求一致；备案服务名称建议使用「三宝殿任务存证服务」类中性表述，**不得出现「积分」「代币」「链上资产」等易被误读为代币化的词**。

### 1.3 关联义务（不并入 V2 两条，但遗漏同样阻断上线）

| 义务 | 依据 | 时点 / 口径 | 与本项目的关系 |
|---|---|---|---|
| ICP 备案 | 《互联网信息服务管理办法》第 4 条、《非经营性互联网信息服务备案管理办法》第 5 条 | 上线前；工信部 `beian.miit.gov.cn`，经**境内接入服务商**提交，材料齐全 20 个工作日内予以备案 | **B-2 硬阻断**；经营性服务还需判断是否需要增值电信业务许可 |
| **安全评估报告** | 安全评估规定第 3 / 6 / 7 条；算法规定第 27 条；区块链规定第 9 条 | **信息服务上线或功能增设前**提交；经**全国互联网安全管理服务平台**报所在地**地市级以上网信部门和公安机关** | 与备案系统是**两套系统、两个动作**，不可互相替代；报告须含功能、部署位置、证照、制度与风险防控效果、评估结论 |

| 用户真实身份核验 | 区块链规定**第 8 条**、安全评估规定第 5 条 | 基于组织机构代码 / 身份证件号码 / 移动电话号码等方式认证；未认证不得提供相关服务 | 与项目「不采集明文 PII、虚拟号占位」存在**实现层冲突**，处置见 §4 R-09 |

## 2. 申报流程与法定期限

### 2.1 统一入口（2026-11-09 起）

```
https://beian.cac.gov.cn  （互联网新技术新应用信息服务备案系统）
├── 注册主体账号 → 完成主体信息填报
├── 算法备案：填报人员入口 / 开始填报 → 《备案填报指南》
├── 区块链备案：同一系统选择备案类别
├── 生成式 AI / 深度合成：同一系统（本项目按 §1.3 单独评估）
└── 首页可按主体名称 / 备案名称 / 备案编号查询已备案信息
```

### 2.2 办理步骤（两类共性）

1. 确定并固定**备案主体**（境内法人 / 非法人组织），与白皮书发行主体、链运营主体、ICP 备案主体保持一致；
2. 完成 **ICP 备案**、境内服务器 / 节点部署（解除 B-1 / B-2 / B-3）；
3. 编制并**在上线前提交安全评估报告**（全国互联网安全管理服务平台）；
4. 编制**算法自评估报告**、**拟公示内容**、区块链服务说明与技术方案；
5. 注册新系统账号、完成主体信息填报，按类别分别提交两类备案；
6. 属地网信部门初审 → 复审 → 会商（区块链答疑列明的状态），按提交时间顺序审核；
7. 材料齐全的予以备案、发放**备案编号**并公示；材料不齐的在法定期限内通知并说明理由 → 修改后**重新排队**；
8. 取得编号后**立即**完成 §2.4 的公示与台账动作。

### 2.3 法定期限表（精确口径，工作日）

| 动作 | 算法推荐服务备案 | 区块链信息服务备案 | 条款 |
|---|---|---|---|
| 提交备案 | 提供服务之日起 **10 个工作日内** | 提供服务之日起 **10 个工作日内** | 算法 §24 / 区块链 §11 |
| 材料齐全 → 予以备案发号 | **30 个工作日内** | **20 个工作日内** | 算法 §25 / 区块链 §12 |
| 材料不齐 → 通知并说明理由 | 30 个工作日内 | 20 个工作日内 | 同上 |
| 备案信息变更 | 变更之日起 **10 个工作日内** | 变更服务项目 / 平台网址之日起 **5 个工作日内** | 算法 §24 / 区块链 §11 |
| 终止服务 → 注销 | 终止之日起 **20 个工作日内** | 终止 **30 个工作日前** | 同上 |
| 定期查验 | 网信部门分级分类安全管理（§23、§28） | 定期查验，须在规定时间登录系统提供信息（§14） | — |
| 日志留存 | 依法留存网络日志（§28） | **不少于 6 个月**（§17） | — |

> **两个易错点**：① 法定「予以备案」期限是**材料齐全后的审查上限**，不是承诺周期；区块链答疑明确**按提交时间分批发放编号、无加急通道**，算法答疑明确**按提交先后审核、修改后以再次提交时间为准**，排期须按「批次 + 重排队」留缓冲。② 算法与区块链的**变更 / 注销时限不同**，台账必须分列，不能共用一套提醒。

### 2.4 取得编号后的持续动作

- 算法规定 **§26**：在对外提供服务的网站 / 应用**显著位置标明备案编号，并提供公示信息链接**；
- 区块链规定 **§13**：在对外提供服务的网站 / 应用**显著位置标明备案编号**；
- 建立备案台账：编号、类别、备案名称、主体、生效日、公示位置、变更记录、注销触发条件、责任人与复核周期；
- **禁止性表述**（2022 年算法备案系统上线通告说明，未被新系统答疑推翻，按保守口径保留）：算法备案**仅对服务及所用技术进行备案，不代表对主体、算法、产品、服务的认可**，任何组织和个人**不得将备案结果用于宣传和其他商业用途**。因此对外只能陈述「已完成 XX 备案（编号 XXX）」这一客观事实，**不得写成「网信办认证 / 官方背书 / 合规认证通过」**。

## 4. 时序冲突与主代理裁决 D-11

### 4.1 冲突陈述

| 来源 | 表述 |
|---|---|
| 算法规定 §24 / 区块链规定 §11 | 「在**提供服务之日起**十个工作日内」填报备案 |
| 区块链旧系统答疑 | 「**产品未正式上线无法提前申请备案**」（新系统指南需复核） |
| `docs/07` §2（修订前）、`docs/03` §6.2、方案 §7.3 G6 | 「**备案回执为上线闸门**」「两份备案回执取得」列为上线前 V2 一票否决 |
| 安全评估规定 §7 | 安全评估报告应在**上线或功能增设前**提交 |

若严格按「上线前必须拿到备案编号」执行，与「未上线不能申请区块链备案」构成**逻辑死锁**；同时把「安全评估（上线前）」与「备案（上线后 10 工作日内）」混为一谈。

### 4.2 裁决（登记为 `CONTRACT.md` §11 **D-11**）

**V2 拆为两段，G6 判定改以 V2-a 为准**：

- **V2-a｜上线前必须完成（G6 一票否决门槛）**
  1. 备案主体确定且与链选型 / 白皮书发行主体一致（B-3、R-13）；
  2. ICP 备案完成、境内服务器 / 节点部署到位（B-1、B-2、R-07）；
  3. **安全评估报告**编制并在上线前提交、回执可核（R-05）；
  4. 算法自评估报告、拟公示内容、区块链服务说明与技术方案定稿（R-11、R-12）；
  5. 备案服务名称定名且不含禁用词（R-08）；
  6. §3 中标记 P0 的产品 / 研发整改全部完成（R-01～R-04、R-09）。
- **V2-b｜L1 灰度启动后按法定期限闭环（上线后复核项，非上线前置）**
  1. 自「提供服务之日」起 **10 个工作日内**在新系统分别提交两类备案；
  2. 材料齐全后按法定期限取得编号（算法 30 / 区块链 20 个工作日，实际按批次排队）；
  3. 取得编号后立即完成显著位置公示与公示链接、建立变更 / 注销台账（§2.4）。

**计时起点定义**：`T = L1 单城灰度面向真实用户开放之日`（方案 §7.3）。L0 在线演示预览**不计入**。

### 4.3 L0 不触发的论证与边界

L0 演示预览同时满足：虚构数据、内存存储刷新归零、无真实用户与资金、不采集真实 PII、不接真实支付 / 大模型 / 公链、**不发动社会公众从事特定活动**。因此在 L0 阶段，V2 状态维持「**未上线、不触发**」，与 `docs/03` / `docs/08` 既有结论一致。

**但必须守住边界**：不得把 L0 链接包装成公众可注册、可发布真实任务、可结算的服务；一旦出现真实用户发布 / 接单行为，即构成「提供服务」，10 个工作日计时开始，`docs/07` G6 需立即复核。

### 4.4 禁止表述清单

- 不得写「已完成两项备案」「已取得备案编号」「网信办认证 / 官方背书 / 合规认证通过」；
- 不得写「V2 已通过」「G6 已通过」「平台已上线 / 已开放注册」；
- 不得把备案结果用于宣传和商业用途（§2.4）；
- 不得把「准备就绪」写成「已提交」，把「已提交」写成「已发号」。
