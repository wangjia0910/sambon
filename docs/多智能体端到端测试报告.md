## 1. 测试方法与环境

### 1.1 为什么用多智能体而非现成测试脚本

既有 `npm test`（301 项）是"开发者视角"的静态/接口回归；本次是"用户视角"的验收——每个智能体只拿到角色剧本和共享 HTTP 客户端（`ops/multiagent-client.mjs`），像真人一样登录、看列表、点操作、等状态变化，**不直接调用 `dispatch()`、不跑现成测试脚本**。这能发现单测覆盖不到的跨角色协作与状态机时序问题。

### 1.2 隔离性

- 独立端口 8793、独立内存 D1 实例，与线上 `sambon.net`（生产 D1）和 WorkBuddy 评审站完全隔离；
- 所有测试邮箱 `*_ma@test.dev`、任务标题含 `MA-pub` 标记，虚构数据；
- 测试结束服务停止即数据清空，不留痕于生产。

### 1.3 协作机制

发布方先发布任务 → 管理员轮询待审核队列并审核/推送 → 接单人轮询任务大厅并接单/提交 → 发布方验收 A、对 B 发起争议 → 管理员裁定 B。角色间不直接传参，只通过共享服务的任务状态变化协作，模拟真实用户"刷新看状态"。

## 4. 核心链路实测数据

### 4.1 任务 A（验收结算链路）

- 状态链：`PENDING_REVIEW → PUBLISHED → DISPATCHING → ACCEPTED → SUBMITTED → SETTLED`
- 结算数值：赏金 **200**、服务费 **10**、质量奖励 **4**（applied=true, cap=50）、接单人到账 **204**、`trigger=verify`、`rule_version=sbc-rule-v1.0`
- 发布方余额：注册 1000 → 发布冻结 367.5（A 210 + B 157.5）→ 632.5；验收是 escrow→接单人转账，不动发布方可用余额（符合设计）

### 4.2 任务 B（争议裁定链路）

- 状态链：`... → SUBMITTED → DISPUTED → SETTLED`
- 发起争议：`transferred=false`、`escrow_total=157.5` 全额继续冻结、`model_decision=null`
- 人工裁定：`resolution=pay_solver`、`arbitrator=人工裁定`、`settlement.trigger=dispute_resolution`；`DisputeResolved.payload.model_decision=null`（模型全程未直判）
- 资金复核：任务 B 的 settle 腿仅 1 个 event_id，结算唯一；接单人/发布方账本均 `balanced=true`、`total_delta=0`

### 4.3 PII 脱敏与账本

- 接单人提交含明文手机号 `13812345678` + 证件号 `110101199001011234` 的成果；
- 落库 `result_preview` = `联系 [已脱敏] 证件 [已脱敏]`，**无 ≥6 位连续数字**，`result_pii_redacted=true`；
- 账本锚定 `pii_on_chain=false`、`task_body_on_chain=false`，merkle_root 存在，哈希链有效。

### 4.4 个性化与隐私信号

- 关闭个性化后 `GET /api/leaderboard/tasks` 返回 `mode=neutral`（服务端强制）；
- GPC 信号（`sec-gpc:1`）注册的用户 `personalized_enabled=false`，`/api/auth/me` 复核一致。

## 6. 发现的问题与定性

| # | 现象                                               | 定性                                                    | 处理建议                                                                |
| - | ------------------------------------------------ | ----------------------------------------------------- | ------------------------------------------------------------------- |
| 1 | admin/publisher 首轮等待超时、多轮次才跑通                    | **测试编排**：串行启动导致角色时间窗错开                                | 非系统缺陷；并行编排下已全通                                                      |
| 2 | `POST /api/admin/cron` 返回 503 `CRON_DISABLED`    | **环境配置**：未设 `CRON_SECRET`                             | 正式运营按 E-04 配置调度器密钥后可用                                               |
| 3 | `POST /api/consents` 用 `kind:'marketing'` 返回 400 | **剧本取值错误**：合法 kind 为 cookie/privacy/tos/aup/analytics | 非缺陷；智能体已如实记录                                                        |
| 4 | 无 `GET /api/tasks/{id}` 单任务路由                    | **接口设计现状**：查单任务需列表示过滤                                 | 非缺陷；前端用列表即可，可选后续增强                                                  |
| 5 | admin3 C-01 并发实测得 400/400 而非 1×200+1×冲突          | **测试样本选择**：任务 A 并发前已 SETTLED，双仲裁拒                     | 非双花；真正并发竞争由 `tests/verify-settlement-concurrency.mjs` 12 项覆盖（含负向注入） |
| 6 | `strong_password_enforced=false`                 | **环境配置**：未开强口令强制                                      | 正式运营建议开启（长度达标的弱口令当前仍可注册）                                            |
| 7 | 裁定响应顶层未暴露 `model_decision`                       | **可观测性小改进**：值在 DisputeResolved.payload 中              | 可在响应顶层补 `model_decision:null` 便于审计                                  |

**无一项为功能逻辑缺陷或红线失守。**
