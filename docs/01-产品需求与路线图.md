## 0. 口径基线（与 CONTRACT.md v0.2 一致，供研发与法务对齐）

### 0.1 统一术语（CONTRACT §1）

| 术语 | 定义 |
|---|---|
| 发布方 Publisher | 提交悬赏、设定验收标准、冻结赏金的主体 |
| 接单人 Solver | 被推送命中、接单、提交成果、获得积分的主体 |
| 任务 Bounty | 全局唯一 `task_id`，含类目、赏金、deadline、验收标准 |
| SBC | Sambon Credit，**平台内贡献积分凭证**；非加密资产、非证券、非支付工具；不可兑付法币、不可转让 |
| 推送 Dispatch | 算法产出有序候选 ＋ 分批触达；一次推送全局唯一 `dispatch_id` |
| 有效完成 | deadline 内提交成果且验收通过（含超时自动验收），并进入结算 |
| `net_sbc` | 用户榜计分口径：**仅已验收通过任务的赏金本金净获得**（CONTRACT v0.2 §1 / §7） |
| 事件 `event_id` | 全局唯一、幂等的业务事件标识；跨模块调用一律携带 `task_id + event_id + version` |

### 0.2 任务状态机（CONTRACT §3，唯一事实源在 C 任务管理系统）

| 状态 | 合法后继 | 超时规则 |
|---|---|---|
| `DRAFT` | `PENDING_REVIEW` / 丢弃 | 7 天清理 |
| `PENDING_REVIEW` | `PUBLISHED` / `REJECTED` | 审核 ≤ 30 min |
| `PUBLISHED` | `DISPATCHING` / `CANCELLED` | 24h 未推送告警 |
| `DISPATCHING` | `ACCEPTED` / `EXPIRED` / `CANCELLED` | 扩量上限后转人工 |
| `ACCEPTED` | `IN_PROGRESS` / `CANCELLED` / `EXPIRED` | 独占 3 min（技能类 15 min） |
| `IN_PROGRESS` | `SUBMITTED` / `EXPIRED` / `DISPUTED` | 按 deadline |
| `SUBMITTED` | `SETTLED` / `DISPUTED` / `IN_PROGRESS`（驳回 ≤ 2 次） | 24h 未验收自动通过 |
| `DISPUTED` | `SETTLED` / `CANCELLED` / `CLOSED` | 72h 结案 |
| `SETTLED` | `CLOSED` | 结算回写 ≤ 10s |
| `REJECTED` / `CANCELLED` / `EXPIRED` / `CLOSED` | 终态 | — |

**并发**：非竞赛制任务采用服务端原子锁 ＋ 先到先得；重复 `event_id` 请求返回原结果，不产生副作用。

### 0.4 关键权重数值（CONTRACT §6 / §7）

**推送打分**（规则版，权重和恒为 1.00，`weight_version = "v1.0"`）

| 因子 | 符号 | 权重 |
|---|---|---|
| `P_accept` | ＋ | 0.30 |
| `P_complete_on_time` | ＋ | 0.35 |
| `C_notify` | − | 0.10 |
| `R_risk` | − | 0.10 |
| `V_fairness` | ＋ | 0.08 |
| `B_supply` | ＋ | 0.07 |

- 硬过滤先于打分：资质不符、超出服务半径、负载已满、日推送频次超限、风控黑名单、发布方与接单人关联。
- 各项先做类目内 P5–P95 截断 ＋ min-max 归一化再加权；等级 / 榜单带来的推送加权**封顶总分 5%**。
- 每条命中必须输出 `reason_codes`，并落库 `task_id / dispatch_id / 候选 / 分数 / weight_version / reason_codes / 批次 / 结果`。
- **LLM 适配层**：仅 `extractTaskStructure()` / `semanticMatchHint()` / `summarizeDispute()` 三个可替换接口，初版返回规则化兜底结果；**不得**让模型决定最终推送名单、积分结算或争议裁定；模型不可用自动降级为规则引擎。

**任务榜维度**（`rank_weight_version = "v1.0"`，合计 1.00；付费置顶不得进入自然排序）

| 维度 | 悬赏价值 | 紧迫度 | 完成可行性 | 发布方信用 | 热度 / 竞争度（过度竞争反向降权） | 质量与清晰度 |
|---|---|---|---|---|---|---|
| 权重 | 0.25 | 0.20 | 0.20 | 0.15 | 0.10 | 0.10 |

**用户榜因子**（合计 1.00；仅「已验收通过任务的净获得 SBC」计入）

| 因子 | 净获得 SBC `net_sbc` | 有效完成单量 | 加权评价（贝叶斯平滑 m=10） | 准时率 |
|---|---|---|---|---|
| 权重 | 0.55 | 0.20 | 0.15 | 0.10 |

**用户榜计入口径（CONTRACT v0.2 §7 / §11 D-03 定稿）**：`net_sbc` **仅指已验收通过任务的赏金本金净获得**；冻结、托管、补偿、邀请、活动、争议中积分一律不计入；**评价 ≥ 4.5 的 ＋2% 高质量奖励（单任务上限 50 SBC）计入接单人可用余额（由生态激励池支出），但不计入 `net_sbc` 与榜单分**（防刷榜、可复算）。方案 §4.1.5「赠送、补偿、邀请、活动奖励一律不计入用户榜」据此延伸。研发实现见 `src/server.mjs` 结算编排（`net_sbc` 只累加 `bounty`，奖励另进 `available`）。

### 0.5 积分规则（CONTRACT v0.2 §5，数值与方案 §4.1.4 一致）

| 行为 | 变动 | 科目 |
|---|---|---|
| 提交审核 | **不划转**：仅合规预检 ＋ 余额预校验，状态 `PENDING_REVIEW` | — |
| **审核通过（进入 `PUBLISHED`）** | 冻结 赏金 ＋ 5% 服务费，写 `CreditFrozen` | 可用 → 冻结 |
| 取消（未接单） | 全额解冻（含 5% 服务费） | 冻结 → 可用 |
| 取消（已接单，发布方原因） | 90% 解冻 ＋ 10% 补偿接单人 | 冻结 → 分账 |
| 有效完成（`SETTLED`） | 转付接单人；**5% 服务费此时才计入平台收入** | 托管 → 可用 / 平台收入 |
| 高质量奖励 | 评价 ≥ 4.5 额外 ＋2% 赏金（单任务上限 50 SBC） | 生态激励支出；**进余额、不计入 `net_sbc`** |
| 超时未完成 | 0，信用分 −5，释放冻结 | 冻结 → 可用 |
| 争议 | 全额转托管，裁定前不得转付 | 冻结 → 托管 |
| 争议退款 / 关闭 / 未成交 | **赏金 ＋ 5% 服务费全额原路退回**（未成交不收服务费） | 托管 → 可用 |
| 违规刷单 | 扣回所得（反向流水冲正）、冻结账户 | 冲正 |

**冻结时点（CONTRACT v0.2 §5 / §11 D-01 定稿）**：统一为「**提交审核 → 审核通过后冻结赏金 ＋ 5% 服务费**」——`POST /api/tasks` 提交审核时只做合规预检 ＋ 余额预校验（**仅校验、不冻结、不写积分流水**），`POST /api/tasks/:id/review` 审核通过进入 `PUBLISHED` 时才冻结（可用 → 冻结）并落 `CreditFrozen`。依据方案 §4.1.4、§4.3.2 与本契约 §5；`CONTRACT.md` v0.1 §8 括注「发布即冻结」及方案 §5.1 第 2 步的时点表述差异，**阶段 C 主代理已定稿（§11 D-01 / D-08），v0.2 §8 括注已修正**，避免 `REJECTED` 产生孤立冻结。

**记账铁律**：不可变流水只追加；冲正以反向流水实现；每条流水含 `event_id / 科目 / 前后余额 / task_id / 规则版本`；**五科目 Σdelta 恒为 0**。

## 1. 目标用户与三类场景（方案 §1.3）

**角色与诉求**（「首版覆盖」按方案 §1.3 原值）

| 角色 | 细分 | 核心诉求 | 首版覆盖 |
|---|---|---|---|
| 发布方 | 个人临时求助 | 快、便宜、别被骗 | P0 |
| 发布方 | 小微商户（批量短任务） | 稳定履约率、可批量发布 | P1 |
| 发布方 | 企业 / 机构（需资质审核、发票） | 合规、对账、税务 | P2 |
| 接单人 | 时间型（本地跑腿 / 代办） | 就近、单多、结算快 | P0 |
| 接单人 | 技能型（维修 / 设计 / 翻译 / 咨询） | 类目精准、单价合理、少纠纷 | P0 |
| 接单人 | 组织型（团队 / 工作室分包） | 多中标、批量任务 | P2 |
| 平台侧 | 运营 / 审核 / 仲裁 / 财务对账 | 可管控、可回放、可对账 | P0 |

**三类场景与推送 / 验收侧重**

| 场景 | 特征 | 推送策略倾向 | 验收口径侧重 |
|---|---|---|---|
| **S1 本地即时跑腿** | 强 LBS、时效 < 2h、金额低、非技能 | 定向派单 ＋ 小批次扩量（首批 K=8、独占 3 min） | 首次接单时长、准时率 |
| **S2 技能型悬赏** | 弱 LBS、时效 1–7 天、需认证 | 邀请制 ＋ 语义精排（首批 K=12、独占 15 min） | 验收通过率、争议率 |
| **S3 众包 / 竞赛制** | 多接单人并行、按结果选优 | 广播抢单 ＋ 分批放量（首批 K=30、分 3 批） | 有效成果数、单人打扰成本 |

> 本轮原型以 **S1 / S2 单接单人闭环**为主跑通链路；S3 多中标、类目专业榜、APP 端对齐按方案 §2.3 裁剪规则列为后续。

> ② 冻结时点落在第 3 步（审核通过），与 CONTRACT v0.2 §5、方案 §4.1.4 / §4.3.2 及研发实现一致；方案 §5.1 第 2 步（PENDING_REVIEW 即冻结）与第 3 步（审核通过发 `TaskPublished`）的时点差异，**阶段 C 主代理已定稿（CONTRACT v0.2 §11 D-01 / D-08）**，v0.2 §8 括注已修正。
> ③ `RiskBlocked` / `PreferenceChanged` 已由 **CONTRACT v0.2 §4 补登记**（§11 D-07）；运行期产生的事件类型必须 ⊆ §4 登记表（自检断言 ⑫ 校验）；`DispatchExposed` / `DispatchIgnored` 登记为 P1 客户端埋点。

**项目初版不做（CONTRACT §0 / §10）**

- 不接真实支付、不接真实大模型、不接公链、不采集真实 PII、不做生产部署、本轮不推送 GitHub。
- SBC 不得实现转让、交易、法币兑换、收益承诺、二级市场类接口或文案；不得存储明文手机号 / 身份证 / 精确定位轨迹，联系方式一律虚拟号占位、日志与事件脱敏。
- 链相关能力仅做「本地 Merkle 摘要 ＋ 可插拔锚定接口」演示，零 PII、零任务正文上链。
- 结算、争议裁定、账号处罚必须保留人工兜底，禁止模型直判；所有演示数据必须是虚构样例。
- **不新增 CONTRACT §8 之外的 HTTP 端点**：取消、举报、注销与删除权、协议确认等均以流程标注 ＋ 纯函数／状态机占位 ＋ 上线闸门核销体现，初版不伪造端点与处置闭环（CONTRACT v0.2 §11 D-09；详见 §9、`review/product-review.md`）。

**裁剪规则（方案 §2.3）**：若 P1 进度受压，按顺序裁剪且不得破坏闭环——S3 众包 / 竞赛制 → 类目专业榜 → APP 端功能对齐（保留小程序）→ 邀请 / 活动类积分规则。**不可裁剪**：任务状态机、积分冻结 / 转付幂等、推送全链路留痕、合规预检与人工仲裁入口。
